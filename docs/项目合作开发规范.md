# MT-EMI 项目合作开发规范

2026.10.11 最后一次修订

## 1. 前言

MT-EMI 项目采用 Git 作为版本控制工具，使用 GitHub 作为代码托管平台。项目组织架构大体如下：

```txt
MT-EMI
├─ assets  // 资源文件夹，存放 ROM 查找表等资源
├─ docs  // 文档文件夹，存放项目开发规范等文档
├─ MT-EMI.gprj
├─ README.md
├─ scripts  // 脚本文件夹，存放工具脚本，如生成查找表的 Python 脚本
├─ sim  // 仿真文件夹，存放仿真测试平台和测试用例
│  └─ tb  // Testbench 文件夹，存放测试平台和测试用例
└─ src  // RTL 源代码文件夹，存放 Verilog 源代码文件
```

其中，`tb` 文件夹应当与 `src` 文件夹的组织结构对偶，确保每个 RTL 文件对应一个或多个 Testbench 文件。

开发人员在开发项目时应当维护好项目的文件组织结构，确保项目的可维护性和可扩展性。

## 2. Git 分支管理规范

项目开发过程中，主要存在三类分支：

1. 主分支 `main`：主分支是项目的主要分支，存放经过充分测试和验证的稳定代码。在开发的任何阶段，都需要保证主分支的代码是可编译和可运行的。主分支的代码应当经过严格的代码审查和测试，确保其质量和稳定性。
2. 开发分支 `dev`：开发分支是项目的主要开发分支，存放正在开发和测试的代码。开发分支的代码可能存在不稳定性和错误，因此在合并到主分支之前，需要经过充分的测试和验证。
3. 功能分支 `feat-<feature_name>`：功能分支是针对特定功能或任务创建的临时分支，用于开发和测试新的功能或修复特定的问题。功能分支的命名应当清晰明了，能够准确描述其所实现的功能或修复的问题。

一个完整的开发周期通常包括以下几个阶段：

1. 功能分支的创建：当开发人员需要实现新的功能或修复特定的问题时，应当从开发分支 `dev` 创建一个新的功能分支 `feat-<feature_name>`。
2. 功能分支的开发和测试：开发人员在功能分支上进行代码开发和测试，确保其功能的正确性和稳定性。在开发过程中，应当遵循项目的代码规范和最佳实践，确保代码的可读性和可维护性。
3. 功能分支的合并：当功能分支的开发和测试完成后，应当将其合并到开发分支 `dev`。在合并之前，应当提交 Pull Request 进行代码审查和测试，确保其质量和稳定性。
4. 开发分支的合并：阶段性开发结束且开发分支 `dev` 的代码经过充分测试和验证后，应当将其合并到主分支 `main`。在合并之前，应当进行代码审查和测试，确保其质量和稳定性。

## 3. Git 提交规范

任何提交都要附带 Message 信息。除了系统自动生成的 Message，其他自己填写的 Message 信息采用约定式提交规范，格式如下：

```txt
<type>: <description>
```

其中，`<type>` 表示提交的类型，`<description>` 表示提交的简要描述。常用的 `<type>` 包括：

- `feat`：新增功能；
- `fix`：修复问题；
- `docs`：文档更新；
- `misc`：其他更新。

如果本次提交对接口、架构等进行了破坏性的修改，则 `<type>` 参数需要改为大写，并在末尾添加 `!`，表示此次提交是破坏性的修改。例如：

```txt
FIX!: 修复了接口不兼容的问题
```

## 4. AI 辅助开发规范

项目允许使用 AI 工具辅助开发，但需要遵循以下规范：

1. AI 工具仅作为辅助工具，开发人员应当对其生成的代码进行充分的审查和测试，确保其质量和稳定性；
2. AI 工具生成的代码应当遵循项目的代码规范和最佳实践，确保其可读性和可维护性。一种可行的方法是让 AI 工具提前阅读 `docs` 文件夹下的所有文档；
3. 不建议让 AI 工具直接修改源代码。建议在项目根目录下新建 `ai_workspace` 文件夹，专门用于存放 AI 工具生成的代码。开发人员可以在该文件夹中进行代码的生成和测试，确保其质量和稳定性后，再将其合并到项目的源代码中。该文件夹已写入 `.gitignore`，不会被提交到 Git 仓库中。
