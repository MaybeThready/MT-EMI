# MT-EMI 项目代码开发规范

2026.10.9 最后一次修订

## 1. 前言

本文档提供了 MT-EMI 项目开发的规范和最佳实践，旨在确保项目开发过程中的一致性、可维护性和高质量代码的产出。所有参与 MT-EMI 项目的开发人员应遵循本规范。

本项目主要采用 Verilog 语言进行 FPGA 开发，具体的版本是 Verilog-2001。但考虑到项目中会涉及到数组的端口传递，因此编译时采取的标准是 SystemVerilog-2017。不过项目的整体文件组织和代码风格仍然遵循 Verilog-2001 的规范。

下面的规范是本项目建议遵守的开发规范。如果开发人员在开发时认为该规范有碍于项目的进展，可以酌情调整。

## 2. 命名规范

### 2.1. 文件命名

文件总是采用蛇形命名法（`snake_case`）进行命名。RTL 源代码文件扩展名总是 `.v`，宏定义头文件扩展名总是 `.vh`，Testbench 文件扩展名总是 `.vt`。

文件名通常有如下几种命名方法：

1. 规定的文件名。如 `top.v`、`defines.vh` 等；
2. 文件内部只包含一个模块，则文件名与模块名相同；
3. 文件内部包含一个顶层模块和多个子模块，则文件名与顶层模块名相同；
4. 文件内部包含多个功能类似的工具类模块，则文件名为这些模块的功能描述。

尽量以方法 2 进行命名。

### 2.2. 模块命名

模块名总是采用蛇形命名法（`snake_case`）进行命名。一个模块的定义格式通常如下：

```verilog
module <module_name>
#(
    parameter <parameter_name> = <default_value>,
    ...
)(
    input <in_port_name>,
    output <out_port_name>,
    ...
);
    ...
endmodule
```

一个模块的变种总是命名为原本模块名加上变种属性后缀的形式。比如关于设备的模块 `device`，其驱动模块总是命名为 `device_driver`。

测试模块总是命名为被测试模块名加上 `_tb` 后缀的形式。比如关于设备的模块 `device`，其测试模块总是命名为 `device_tb`。

模块的实例总是命名为被实例化模块名（或其简称）加上 `_u` 后缀的形式。如果有多个实例，则在 `_u` 后加上数字编号。比如关于设备的模块 `device`，其实例总是命名为 `device_u`，如果有多个实例，则命名为 `device_u1`、`device_u2` 等。

一个模块实例的定义格式通常如下：

```verilog
<module_name> #(
    .<parameter_name>(<value>),
    ...
) <instance_name> (
    .<in_port_name>(<signal_name>),
    .<out_port_name>(<signal_name>),
    ...
);
```

### 2.3. 信号命名

所有信号的命名均采用蛇形命名法（`snake_case`）进行命名。信号的命名应当做到见名知意，并且尽量简短。如果信号命名具有一定歧义，需要在信号首次出现处或定义处添加注释进行说明。

如果有两个信号名称相同但类型不同，则需要在信号名称后加上类型后缀进行区分。常见的类型后缀有 `_r`（寄存器）、`_w`（线网）。一种比较常见的场景是为接口输出信号定义一个寄存器信号用于寄存器化输出，则该寄存器信号可以命名为接口输出信号名称加上 `_r` 后缀。

如果信号是低电平有效，需要加上后缀 `_n`。比如一个低电平有效的复位信号可以命名为 `rst_n`。高电平有效信号可以不加后缀，但在某些情况下也可以加上后缀 `_p` 以示区分。

部分信号可以采用缩写的形式进行命名。常见的缩写有 `clk`（时钟）、`rst`（复位）、`en`（使能）、`addr`（地址）、`data`（数据）、`valid`（有效）、`ready`（就绪）、`stc`（当前状态）、`stn`（下一状态）等。

### 2.4. 参数与宏定义命名

所有参数和宏定义的命名均采用大写蛇形命名法（`UPPER_SNAKE_CASE`）进行命名。对于一些需要公共开放对接的参数和宏定义，需要在定义处添加注释进行说明，包括参数含义、单位等。比如，对于 Q 格式浮点常数的定义，需要在定义处添加注释说明其 Q 格式和对应的十进制数值。

参数分为 `parameter` 和 `localparam` 两种类型。`parameter` 是模块的可配置参数，通常用于模块的功能配置和接口定义；`localparam` 是模块的局部参数，通常用于模块内部的计算和状态机定义。

所有宏定义只能在 `defines.vh` 文件中进行定义，禁止在其他文件中定义宏。另外，接口内部不建议直接调用宏定义，而是通过 `parameter` 参数传递的方式进行配置，仅在例化模块时才使用宏定义进行参数传递。这样做是为了方便进行模块测试。

### 2.5. 特殊注释规范

`// TODO:` 注释用于标记需要后续处理的代码，通常用于标记需要进一步完善或优化的功能。`// FIXME:` 注释用于标记需要修复的代码，通常用于标记存在问题或错误的功能。`// NOTE:` 注释用于标记需要注意的代码，通常用于标记一些特殊情况或重要信息。

需要为每个 RTL 源代码文件撰写文件头。文件头内容不做太多要求，但必须包含对该文件内容的简要说明。测试文件需要写清楚测试内容。下面是一个可行的文件头示例：

```verilog
/**
 * 文件主要内容描述
 */
```

需要为每个公共接口撰写接口注释。接口注释与文件头格式类似，但是要能够清除地说明接口的功能、输入输出信号的含义、时序要求、调用方法等。如果接口比较复杂也可以适当精简，但需要与团队成员进行沟通。

## 3. 代码格式

### 3.1. 缩进与对齐

每次缩进均采用 4 个空格进行缩进，禁止使用制表符（Tab）进行缩进。可以在代码编辑器中设置自动将 Tab 转换为四个空格，以确保代码缩进的一致性。这里之所以禁止使用制表符，是因为不同的编辑器和查看工具对制表符的显示宽度可能不同，容易导致代码在不同环境下显示不一致，从而影响代码的可读性。

### 3.2. 代码块与空行

每个代码块相对于其父代码块缩进 4 个空格。每个代码块之间应当使用一个空行进行分隔，以提高代码的可读性。对于较长的代码块，可以在代码块内部适当使用空行进行分隔，以提高代码的可读性。

### 3.3. begin-end 块的使用

所有的 begin-end 块必须使用 `begin` 和 `end` 关键字进行包裹，除了在单行语句中可以省略 `begin` 和 `end` 关键字。这种情况常见于状态机状态转移逻辑的编写中。

`begin` 和 `end` 关键字必须单独占据一行，并且与其所在的代码块对齐，其子代码块必须缩进 4 个空格。下面是一个示例：

```verilog
always @(posedge clk or negedge rst_n)
begin
    if (condition1)
    begin
        a <= b;
        b <= c;
    end
    else if (condition2)
    begin
        case (state)
            STATE1:
            begin
                a <= d;
                b <= e;
            end

            STATE2:
            begin
                a <= f;
                b <= g;
            end

            default:
            begin
                a <= h;
                b <= i;
            end
        endcase
    end
    else
    begin
        a <= d;
        b <= e;
    end
end
```

## 4. 设计规范

### 4.1. 信号设计规范

所有 IO 信号均设计为线变量（wire），因此不需要在端口定义时指定类型。但是大部分模块的输出都要进行锁存，因此在模块内部需要定义一个寄存器信号用于锁存输出信号，最后通过 `assign` 语句将寄存器信号赋值给输出信号。这样做的好处是可以避免在端口定义时指定类型，从而提高代码的可读性和可维护性。

### 4.2. 位宽声明规范

大部分数据都要声明位宽，例如 `4'd3`、`8'hFF` 等。

全 0 或全 1 赋值可以不声明位宽，写作 `'0` 或 `'1`，比如 `assign a = '0;`、`assign b = '1;`。但是在某些情况下，仍然需要声明位宽，例如在状态机的状态定义中，需要声明位宽以确保状态编码的正确性。

参数化位宽需要使用 `{}` 进行拼接，例如 `{WIDTH{1'b0}}`、`{WIDTH{1'b1}}` 等。

### 4.3. 组合逻辑设计规范

单项组合逻辑应当尽可能地简单。如果组合逻辑比较复杂，需要将其拆分为多个简单组合逻辑块，运用流水线的形式转化为时序逻辑电路实现，以避免时序冲突。

除了部分十分简短的组合逻辑可以使用 `assign` 语句进行定义外，其他组合逻辑应当使用 `always @(*)` 块进行定义。在 `always @(*)` 块中，必须使用阻塞赋值进行变量赋值。同时，为避免综合出时序逻辑，所有的条件分支必须覆盖所有的情况，比如在 `if-else` 语句中，必须包含 `else` 分支；在 `case` 语句中，必须包含 `default` 分支。

### 4.4. 时序逻辑设计规范

该项目除了部分 IP 核外，其他所有模块均工作在同步时钟上升沿、异步复位下降沿的时序逻辑电路中，即所有的时序逻辑应当使用 `always @(posedge clk or negedge rst_n)` 块进行定义。

其中，`clk` 是模块的时钟信号，在不同模块中可能有不同的名称，但在系统上最终都指向同一个时钟信号 `clk_sys`。`rst_n` 是模块的复位信号，通常绑定在扩展板按键 `S0` 上，低电平有效。

在 `always @(posedge clk or negedge rst_n)` 块中，必须使用非阻塞赋值进行变量赋值。
